# Промпт для Codex: CI/CD и деплой Spring Boot в Kubernetes

## Роль и формат работы

Действуй как Senior DevOps Engineer и опытный Java/Spring Boot разработчик. Работай с существующим приложением в текущем репозитории. Не предполагай заранее конкретные имена папок, пакетов, модулей или файлов: сначала изучи репозиторий, определи его фактическую структуру и адаптируй изменения к ней.

Цель — подготовить воспроизводимый локальный CI/CD-процесс для приложения на Java 21 с Spring Boot, Gradle Kotlin DSL, PostgreSQL, Docker, Jenkins, Minikube и Helm, а также настроить Prometheus и Grafana.

Вноси реальные изменения в проект, когда среда позволяет. Перед изменением существующих файлов изучи их содержимое и сохрани совместимые настройки. Не заменяй файлы целиком без необходимости. Не выдумывай уже существующие команды, результаты тестов или инфраструктуру. Если действие невозможно выполнить, объясни причину и укажи точные следующие шаги.

## 1. Сначала изучи проект

1. Определи текущую структуру репозитория, используемые версии Java, Spring Boot и Gradle, наличие Gradle Wrapper, тестов, Docker-конфигурации, CI/CD и Kubernetes/Helm-манифестов.
2. Определи, использует ли проект `build.gradle.kts` (Gradle Kotlin DSL). Если проект уже использует другую систему сборки, не выполняй массовую миграцию без необходимости: сообщи об этом и предложи безопасный план.
3. Найди существующие точки входа, конфигурацию приложения, подключение к базе данных и тесты.
4. Составь краткий план изменений с учётом найденного состояния, затем выполняй его поэтапно.
5. Не создавай дубликаты конфигураций или компонентов, если эквивалент уже существует.

## 2. Технологические требования

- Java 21.
- Spring Boot.
- Gradle Kotlin DSL (`build.gradle.kts`) и Gradle Wrapper.
- PostgreSQL.
- Docker-образ приложения.
- Jenkins Pipeline в `Jenkinsfile`.
- Minikube как локальный Kubernetes-кластер.
- Helm для установки и обновления приложения.
- Prometheus и Grafana для метрик приложения и кластера.
- Конфигурация должна подходить для локальной разработки и допускать дальнейший перенос в более серьёзное окружение.

Используй совместимые стабильные версии зависимостей и инструментов. Не обновляй версии без причины. Проверяй совместимость плагинов Gradle, Spring Boot и Java 21.

## 3. Минимально работающее Web-приложение

Убедись, что в проект добавлены все необходимые зависимости для минимального работающего Spring Boot Web-приложения. Как минимум, для стандартного Spring MVC приложения нужна зависимость:

- `org.springframework.boot:spring-boot-starter-web`

Также проверь, что есть необходимые плагины Spring Boot и Java для текущей версии Gradle Kotlin DSL, корректный класс приложения с `@SpringBootApplication` и тестовая конфигурация.

Если приложение уже содержит Web-зависимость и корректно запускается, не добавляй дубликат. Если отсутствует минимальная HTTP-точка входа, добавь простой endpoint или сохрани имеющийся, чтобы можно было проверить запуск приложения HTTP-запросом. Добавь базовый тест контекста или Web endpoint.

Для требований ниже, если соответствующие функции нужны приложению, добавь и настрой:
- Spring Data JPA — для ORM и доступа к данным;
- PostgreSQL JDBC driver;
- Spring Boot Actuator;
- Micrometer Prometheus Registry;
- тестовые зависимости Spring Boot;
- миграции БД через Flyway или Liquibase, если приложение управляет схемой БД.

Не добавляй JPA, миграции или иные зависимости без необходимости, если проект их не использует; объясни решение. Не используй `ddl-auto: update` как production-стратегию миграций.

## 4. Версионирование

Требуемая схема:
- рабочие ветки `<type>/<short-topic>` (`feature/*`, `fix/*`, `chore/*`): версия приложения вида `1.1.1-SNAPSHOT`;
- после merge pull request в интеграционную ветку `stayledger-codex`: release-версия вида `1.1.1`.

Реализуй версионирование единообразно для Gradle-артефакта, метаданных приложения, Docker-образа и параметров Helm. Не используй `latest` как основной идентификатор релиза. Предпочитай неизменяемые теги и/или идентификатор сборки для однозначной идентификации артефакта.

Сначала выясни, как сейчас задаётся версия. Сделай один авторитетный и понятный механизм определения версии. Jenkins должен определять версию по ветке и принятой в репозитории схеме релизов, не полагаясь на ручное переключение версии перед каждой сборкой.

Не допускай неоднозначного повторного использования версии: если после выпуска `1.1.1` начинается следующая разработка, она должна перейти на `1.1.2-SNAPSHOT`, а не продолжать использовать `1.1.1-SNAPSHOT`. Опиши, как определяется следующая версия. Если в проекте нет политики увеличения версии, предложи простую прозрачную политику и зафиксируй её до реализации.

Для Gradle Kotlin DSL используй Gradle Wrapper и корректный параметр версии, например `-PappVersion=...`, только если он согласован с существующей конфигурацией. Не допускай, чтобы Docker-тег и версия собранного JAR расходились.

## 5. Сборка и тесты

Настрой воспроизводимые команды с Gradle Wrapper:
- проверка версии Gradle и Java;
- запуск тестов;
- сборка приложения;
- создание исполняемого Spring Boot JAR.

В Jenkins обязательно выполняй тесты до публикации образа и деплоя. При ошибке тестов или сборки pipeline должен завершаться неуспешно и не должен деплоить новый артефакт.

Проверь, что `.gitignore` исключает генерируемые файлы и локальные секреты. При необходимости добавь `.dockerignore`, адаптированный к фактическому проекту.

## 6. Docker

Подготовь production-ориентированный Dockerfile, совместимый с Java 21 и реальным способом сборки проекта. По возможности используй multi-stage build и запускай приложение не от root.

Требования:
- Docker-образ собирается воспроизводимо;
- версия приложения передаётся в сборку явно;
- не копируются Git-данные, локальные IDE-файлы, секреты и ненужные артефакты;
- не встраиваются пароли и другие секреты в образ;
- команда запуска соответствует фактическому артефакту Spring Boot;
- базовые образы и их обновление документированы.

Определи подходящий для Minikube способ доставки образа. Если внешний registry не используется, обеспечь передачу/сборку образа именно в среде Minikube. Не предполагай, что образ, собранный Docker daemon на хосте или в контейнере Jenkins, автоматически доступен кластеру. Если используется registry, настрой публикацию и доступ к нему без хранения credentials в исходниках.

## 7. PostgreSQL

Настрой PostgreSQL для локального Kubernetes-окружения через поддерживаемый Helm chart или существующее инфраструктурное решение проекта.

Требования:
- приложение обращается к БД по Kubernetes Service DNS, а не по `localhost`;
- данные PostgreSQL хранятся на PersistentVolumeClaim, если выбранный локальный драйвер Minikube поддерживает его;
- параметры подключения настраиваются через переменные окружения;
- пароль хранится в Kubernetes Secret или внешнем менеджере секретов, но не в Git и не в открытом `values.yaml`;
- готовность базы и порядок запуска приложения обрабатываются корректно;
- схема базы управляется миграциями, если они нужны приложению;
- предусмотрены инструкции по проверке подключения, диагностике и удалению/сохранению данных.

Не предполагай, что Secret, созданный для приложения, автоматически подходит стороннему Helm chart PostgreSQL: проверь точные требования и имена ключей выбранной версии chart. Не используй демонстрационный пароль как production-секрет.

## 8. Helm и Kubernetes

Создай или адаптируй Helm chart, соответствующий фактическому проекту. Не навязывай конкретную структуру каталогов, если в репозитории уже приняты другие соглашения.

Минимально необходимые ресурсы, если они применимы:
- Deployment;
- Service;
- ConfigMap для несекретной конфигурации;
- ссылка на Kubernetes Secret для секретных значений;
- readiness и liveness probes;
- requests/limits CPU и памяти;
- корректные labels;
- настройки образа и его тега через values;
- настройки окружения без захардкоженных секретов.

Для Spring Boot Actuator настрой health probes так, чтобы они действительно работали с используемой версией Spring Boot. Не публикуй Actuator endpoints наружу без необходимости. Проверь Helm chart командами `helm lint` и `helm template` до деплоя.

Разделяй общие значения chart и значения конкретного окружения. Обеспечь возможность менять версию Docker-образа через параметры Helm из Jenkins. Используй namespace для приложения и отдельный namespace для мониторинга, если это упрощает управление ресурсами.

Поддержи безопасное обновление через `helm upgrade --install`, проверку результата и инструкции по rollback.

## 9. Configs и secrets

Предусмотри и кратко сравни варианты:
1. ConfigMap + Kubernetes Secret, а доступ к секретам ограничен; подходит для простого локального старта.
2. SOPS + age для зашифрованных секретов в Git.
3. Vault + External Secrets Operator или другой внешний secret manager для более серьёзного окружения.

Для первой реализации выбери самый простой безопасный вариант, соответствующий проекту, но не создавай открытые секреты в Git. Учитывай, что Base64 в Kubernetes Secret — это кодирование, а не шифрование. Не передавай секреты через аргументы командной строки, если это может привести к утечке в логи или process list. Для Jenkins credentials используй механизм Credentials Store и маскирование значений. Не печатай секреты в pipeline logs.

## 10. Jenkins Pipeline

Создай или адаптируй `Jenkinsfile` с понятными этапами. Например:
1. Checkout.
2. Проверка версии Java/Gradle и подготовка версии приложения.
3. Unit tests и проверки.
4. Сборка Spring Boot artifact.
5. Сборка Docker image.
6. Публикация или передача образа в Minikube.
7. Проверки Helm chart.
8. Деплой через Helm.
9. Ожидание rollout и smoke tests.

Требования:
- рабочие ветки `feature/*`, `fix/*` и `chore/*` формируют SNAPSHOT-версии, `stayledger-codex` — release-версии;
- release-деплой выполняется только после успешных проверок;
- ветки и условия запуска явно определены;
- credentials хранятся в Jenkins Credentials Store;
- pipeline не выводит секреты в логи;
- при ошибке deployment pipeline завершается неуспешно;
- по возможности добавь проверку доступности HTTP endpoint после деплоя;
- реализуй timeout и очистку временных ресурсов;
- не используй `sudo`, привилегированный Docker или доступ к Docker socket без обоснования и описания рисков;
- явно документируй требования к Jenkins agent и доступу к Minikube/registry.

Не предполагай, что Jenkins внутри Docker автоматически видит kubeconfig, Docker daemon или образы Minikube. Укажи, что нужно настроить для выбранной топологии. Если топология Jenkins ещё не определена, предложи поддерживаемый вариант по умолчанию и перечисли его ограничения.

## 11. Prometheus и Grafana

Подготовь установку мониторинга через Helm, предпочтительно используя `kube-prometheus-stack`, если это совместимо с выбранным окружением.

Нужно:
- Prometheus для сбора метрик;
- Grafana для визуализации;
- метрики Kubernetes и Pod;
- Spring Boot Actuator;
- Micrometer Prometheus Registry;
- endpoint `/actuator/prometheus`;
- ServiceMonitor или иной корректный механизм обнаружения приложения, совместимый с конфигурацией Prometheus Operator;
- базовые инструкции для доступа к Grafana через port-forward;
- способ проверить, что Prometheus действительно получает метрики приложения.

Если мониторинг БД нужен, добавь PostgreSQL exporter и опиши его конфигурацию без открытого хранения credentials. Учитывай ресурсы локального Minikube: задай разумные requests/limits и предупреди, если полный стек может требовать увеличения CPU/памяти.

Не считай мониторинг готовым только потому, что Helm release установлен: проверь target health и наличие метрик.

## 12. Проверки и критерии готовности

По завершении выполни доступные проверки и укажи фактический результат каждой:
- Gradle Wrapper запускается с Java 21;
- тесты проходят;
- приложение собирается;
- Docker image собирается;
- Helm chart проходит lint и template;
- Kubernetes ресурсы становятся Ready;
- приложение доступно через Service/port-forward;
- приложение подключается к PostgreSQL;
- health endpoint возвращает успешный статус;
- Prometheus обнаруживает приложение и получает метрики;
- Grafana доступна и использует Prometheus как источник данных;
- Jenkins pipeline корректно обрабатывает SNAPSHOT и release-сценарии;
- rollback документирован и проверен, если среда позволяет.

Не заявляй, что проверка прошла, если ты её фактически не запускал. Если нет доступа к Docker, Minikube или Jenkins, выполни статические проверки, отметь ограничения и предоставь точные команды для проверки пользователем.
